## JVM 的运行时数据区由哪些部分组成？

JVM 在运行时会将所管理的内存划分为若干区域，理解这些区域是掌握垃圾回收、内存溢出与线程模型的基础。按是否线程私有，可分为两类。

线程私有区域随线程的创建而创建、销毁而销毁：

- **程序计数器**：一小块内存，记录当前线程正在执行的字节码指令地址；若当前执行的是 `native` 方法，该值为 undefined。它是唯一不会抛出 `OutOfMemoryError` 的区域，作用是线程切换后能恢复到正确的执行位置。
- **Java 虚拟机栈**：对应 Java 方法调用的栈结构，每次方法调用会创建一个栈帧，存放局部变量表、操作数栈、动态链接、方法出口等信息。递归深度超出栈容量触发 `StackOverflowError`。规范允许虚拟机栈固定大小或动态扩展，但 HotSpot 采用固定大小（`-Xss`），因此 OOM 并非「栈扩展失败」，而是创建新线程时无法为其分配栈。
- **本地方法栈**：与虚拟机栈作用类似，服务于 `native` 方法（如 JNI 调用的 C/C++ 代码），HotSpot 中与虚拟机栈合并实现。

线程共享区域为所有线程共用，也是垃圾收集的主要关注对象：

- **堆**：JVM 中最大的一块内存，存放对象实例与数组，是 GC 的主战场，通常按分代划分为新生代（Eden 与两个 Survivor 区）和老年代。
- **方法区**：存储已被加载的类信息（字段与方法描述、方法字节码）、**运行时常量池**等。JDK 8 之前称为"永久代"，位于堆内、容易 OOM；JDK 8 起改为**元空间（Metaspace）**，使用本地内存，理论上受系统内存限制，但同样可能溢出。两个常见误区：JIT 编译后的本地代码存放在 HotSpot 独立的**代码缓存（CodeCache）**中，不属于方法区（元空间）；类的静态变量自 JDK 7 起随 `Class` 对象移入堆，同样不在方法区。

需要厘清的易混点：基本类型变量与对象引用存于栈帧的局部变量表，对象实例本身在堆中；方法区在 JDK 8 前后的实现差异（永久代到元空间）、以及「运行时常量池在方法区、字符串常量池自 JDK 7 起在堆」是面试高频追问点，应明确区分。

### 高频延伸
- **堆分代比例**：JDK 8 默认 `-XX:NewRatio=2`（新生代:老年代 = 1:2）、`-XX:SurvivorRatio=8`（Eden:S0:S1 = 8:1:1），且比例随收集器而变。
- **各区域的 OOM 与参数**：堆溢出报 `OutOfMemoryError: Java heap space`（`-Xms`/`-Xmx`）；元空间溢出报 `OutOfMemoryError: Metaspace`（`-XX:MetaspaceSize`/`-XX:MaxMetaspaceSize`，JDK 8 之前为 `PermGen space`，对应 `-XX:MaxPermSize`）。
- **为何用元空间替换永久代**：核心原因是规避永久代固定大小带来的 OOM、降低调优成本，并与 JRockit/J9 等 JVM 实现对齐。
- **JDK 8 服务端默认收集器**：Parallel Scavenge + Parallel Old，并非 CMS；G1 到 JDK 9 才成为默认。
- **局部变量表的存储单位**：以**变量槽（Slot）**为单位，HotSpot 中每个槽占 32 位——`boolean`/`byte`/`char`/`short`/`int`/`float`/`reference` 各占 1 个槽，`long`/`double` 占 2 个**连续**槽（规范只规定成对占用，不强制槽宽与对齐）；存对象时槽内是**指向堆中实例的引用**，实例本身仍在堆；实例方法的第 0 个槽固定为 `this`，静态方法没有。
- **运行时数据区之外的直接内存**：NIO 的 `DirectByteBuffer` 使用它，不受 `-Xmx` 约束，由 `-XX:MaxDirectMemorySize` 限制，溢出同样抛 `OutOfMemoryError`（缓冲区本身的用法见 IO 模块的[『NIO 的三大核心组件是什么？』](/java/io/#nio-的三大核心组件是什么)）。
- **`MetaspaceSize` 不是初始大小**：`-XX:MaxMetaspaceSize` 是上限（**默认不限制**，受本地内存约束），而 `-XX:MetaspaceSize` 是**首次触发 Full GC 的阈值**，容易记反。
- **CodeCache 打满的表现**：不是抛异常，而是 JIT 编译被禁用、退化为解释执行（性能骤降而非直接崩溃）；上限由 `-XX:ReservedCodeCacheSize` 控制（JDK 8 默认约 240MB）。

## 对象在堆中是如何分配与晋升的？

结论：新对象**优先在新生代的 Eden 区分配**；大对象直接进老年代；经历若干次 Minor GC 仍存活的对象晋升到老年代。这套规则的目标只有一个——**尽量减少 Full GC**。

- **在 Eden 分配**：绝大多数对象都在 Eden 出生。Eden 空间不足时触发 **Minor GC**（只回收新生代）。
- **TLAB（线程本地分配缓冲）**：Eden 被切成若干 TLAB，线程优先在自己的 TLAB 内分配，避免多线程争抢同一块内存而频繁加锁（`-XX:+UseTLAB`，默认开启）。
- **大对象直接进老年代**：需要连续大块内存的对象（如长数组）直接在老年代分配，避免在 Eden 与 Survivor 之间反复复制。由 `-XX:PretenureSizeThreshold` 控制，**默认 0（不启用）**，且该参数只对 Serial / ParNew 生效，Parallel Scavenge 会忽略。
- **长期存活的对象晋升**：对象每熬过一次 Minor GC，年龄加一，达到 `-XX:MaxTenuringThreshold`（**默认 15**）后晋升老年代。
- **动态年龄判定**：若 Survivor 中同一年龄的对象大小之和超过 Survivor 空间的一半，则**该年龄及以上的对象直接晋升**，不必等到 15 岁——这是 HotSpot 为避免 Survivor 溢出做的自适应。
- **空间分配担保**：Minor GC 前会检查**老年代剩余连续空间**是否大于历次晋升对象的平均大小，不够就直接改为 **Full GC**。历史上还多一层更严格的检查——"是否大于新生代所有对象总大小"，由 `-XX:HandlePromotionFailure` 控制；但**该参数自 JDK 6u24 起实际恒按"允许担保"处理、已基本失效，并在后续版本被彻底移除**（本机 JDK 17 实测报 `Unrecognized VM option`）。

### 高频延伸
- **为什么要有 Survivor 区，只留 Eden 和老年代不行吗**：Survivor 是 Eden 与老年代之间的缓冲带——让"活过一轮但活不久"的对象有地方待着、不急着进老年代，从而放慢老年代增长速度、降低 Full GC 频率。复制算法本身也要求有一块空闲的"去向"区域。
- **为什么是两个 Survivor**：复制算法需要一个空的去向区。S0 与 S1 交替充当"从"与"到"，每轮 GC 后总有一块是空的。
- **对象一定分配在堆上吗**：不一定——这是常识而非规范。**逃逸分析**判定对象未逃逸后，HotSpot 通过**标量替换**把它拆成若干局部变量，效果上等同于"栈上分配"（`-XX:+DoEscapeAnalysis`，默认开启）。
- **TLAB 会不会浪费内存**：会。每个线程独占一小块，线程多而分配少时碎片化明显；换来的好处是分配时不必走全局锁，多数场景更划算。
- **为什么大对象阈值默认不启用**：因为"多大算大"高度依赖业务；设错会把本该在新生代快速回收的大对象堆进老年代，反而加剧 Full GC。实践中多是先开启、再按压测结果调。

## 如何判断一个对象已经"死亡"？

结论：HotSpot 用**可达性分析**判断对象存活，而不是引用计数——从一组 **GC Roots** 出发遍历引用链，不可达的对象才可回收。且对象"死亡"要经历**两次标记**，中间有一次 `finalize()` 自救的机会。

- **为什么不用引用计数**：它回收及时、实现简单，但**无法解决循环引用**（A 引用 B、B 又引用 A，两者计数都不为 0 却已经不可达），且每次赋值都要维护计数、有运行时开销。主流 JVM 都不用。
- **可达性分析**：从 GC Roots 向下搜索，走过的路径叫**引用链**；没有任何引用链相连的对象判定为不可达。
- **GC Roots 包括哪些**：虚拟机栈中局部变量表引用的对象、方法区中静态属性与常量引用的对象、本地方法栈中 JNI 引用的对象，以及被同步锁持有的对象、活跃线程等。
- **两次标记与 `finalize` 自救**：不可达对象先被第一次标记并筛选——若它重写了 `finalize()` 且尚未执行过，就放进 `F-Queue` 由低优先级线程执行；在 `finalize()` 中若重新与引用链上的对象建立关联，就能逃过本次回收，但**只能自救一次**。

### 高频延伸
- **可达性分析期间引用变了怎么办**：靠 **OopMap** 记录栈与寄存器里哪些位置是引用，把 GC Roots 的枚举耗时压到极低；并且只在**安全点（Safepoint）**才停下来做根枚举，这同时也是 STW 停顿的主要来源之一。
- **安全点和安全区域是什么**：安全点是代码中"引用关系明确"的位置，线程到达后才允许 GC；**安全区域**用于 `sleep`/阻塞中的线程——进入时声明自己处于安全区域，GC 期间无需理会它。
- **根枚举一定要 STW 吗**：要。引用关系在持续变化，不停顿就无法得到一致快照。但**并发标记**阶段（CMS、G1）可以让用户线程与 GC 线程并行跑，代价是可能漏标，需要写屏障补救。
- **`finalize()` 为什么不可靠**：执行时机不确定、可能永远不执行（`F-Queue` 只是"尽力"）、会延长对象存活、拖慢 GC。释放资源应用 try-with-resources 或 `Cleaner`。
- **引用计数真的一无是处吗**：不是。它回收及时、实现简单，Python 等语言仍在用；Java 不用它主要是循环引用与维护成本的问题。

## 常见的垃圾回收算法有哪些？

结论：四种基础算法——**标记-清除**、**标记-复制**、**标记-整理**、**分代收集**。前三者各有短板，所以实际 JVM 采用**分代收集**：新生代用复制算法（对象死亡率高、复制成本低），老年代用标记-清除或标记-整理（存活率高、不适合复制）。

- **标记-清除（Mark-Sweep）**：标记存活对象、回收未标记的。实现简单，但**会产生内存碎片**，且清除效率随对象数增加而下降。
- **标记-复制（Mark-Copy）**：内存分两块、每次只用一块；回收时把存活对象**整块复制**到另一块再清空原块。无碎片、分配快（只需移动指针）；但**内存利用率低**，存活对象多时复制开销大。
- **标记-整理（Mark-Compact）**：标记后把存活对象向一端移动，再清理边界外内存。无碎片、不浪费空间，但**移动对象要更新所有引用**，成本高、停顿长。
- **分代收集（Generational）**：按对象存活时长划分区域，不同区域用不同算法——新生代"朝生夕死"用复制，老年代存活率高用标记-清除 / 标记-整理。
- **两个绕不开的指标**：**Stop The World（STW）**指 GC 时暂停用户线程；**吞吐量**（用户代码时间占比）与**停顿时间**（单次 STW 时长）通常互相矛盾，调优就是在两者之间取舍。

### 高频延伸
- **为什么新生代用复制、老年代不用**：新生代对象绝大多数活不过一轮，存活对象极少，复制成本极低还顺带整理了内存；老年代存活率高，若也复制则代价极高且浪费空间。
- **为什么新生代要分 Eden 与两个 Survivor**：Eden 占大头（默认 8/10），两个 Survivor 各 1/10 交替使用。这样复制算法只需一小块空闲区，内存利用率远高于"两块对半分"的 50%。
- **标记-整理和标记-清除怎么选**：追求吞吐、能容忍碎片 → 标记-清除（CMS）；追求无碎片、容忍较长停顿 → 标记-整理（Serial Old、Parallel Old）。
- **垃圾回收一定要 STW 吗**：不是必然，但**根枚举阶段必然停顿**。CMS 与 G1 把最耗时的标记、清理做成并发执行，把停顿压到短暂的两三个阶段——这正是"低延迟收集器"的本质。
- **吞吐量与停顿时间为什么矛盾**：并发收集会占用 CPU 与用户线程抢资源，还需写屏障等额外开销；想缩短单次停顿就得让并发推进更频繁，整体吞吐随之下降。所以第一步是先明确业务要"高吞吐"还是"低延迟"。

## 常见的垃圾收集器有哪些？JDK 8 默认是哪个？

结论：按"新生代 / 老年代"与"追求吞吐 / 追求低延迟"两条线，主要有 **Serial、ParNew、Parallel Scavenge、Serial Old、Parallel Old、CMS、G1** 这些组合（外加 JDK 11 起的 ZGC、Shenandoah）。**JDK 8 服务端默认是 Parallel Scavenge + Parallel Old；JDK 9 起 G1 成为默认。**

- **Serial / Serial Old**：单线程、全程 STW，简单高效，适合客户端模式或小内存场景（`-XX:+UseSerialGC`）。
- **ParNew**：Serial 的多线程版，只负责新生代，常与 CMS 搭配。
- **Parallel Scavenge / Parallel Old**：多线程、**关注吞吐量**（可用 `-XX:MaxGCPauseMillis`、`-XX:GCTimeRatio` 调节），JDK 8 的默认组合。
- **CMS（Concurrent Mark Sweep）**：以**最短停顿**为目标的老年代收集器，用标记-清除，有并发标记与并发清理，也有著名的"并发模式失败"。
- **G1（Garbage First）**：把堆切成大量 Region，**可预测停顿模型**（`-XX:MaxGCPauseMillis`，默认 200ms），用 `Mixed GC` 回收收益最高的 Region；JDK 7 引入、**JDK 9 起成为默认**。
- **ZGC / Shenandoah**：JDK 11 起的超低停顿收集器，停顿与堆大小基本无关；ZGC 于 **JDK 15 转正**。

怎么选：

- 内存小、要简单 → Serial。
- 要吞吐量（批处理、计算型） → Parallel Scavenge + Parallel Old。
- 要低延迟（Web 服务） → 优先 G1；对停顿极敏感再考虑 ZGC。
- **CMS 已过时：JDK 9 标记废弃、JDK 14 移除**，新项目不应再选。

### 高频延伸
- **GC 里的"并行"和"并发"有什么区别**：**并行**指多条 GC 线程同时工作，但**用户线程仍暂停**（STW）；**并发**指 GC 线程与用户线程同时运行。并行为了吞吐，并发为了停顿。
- **CMS 的"并发模式失败"是什么**：并发清理阶段用户线程还在分配对象，若老年代在清理完成前被填满，CMS 只能退化成 **Serial Old 单线程 Full GC**，停顿陡增到秒级。诱因通常是并发阶段预留空间不足或对象晋升过快。
- **CMS 还有哪些坑**：标记-清除会产生**内存碎片**（靠 `-XX:+UseCMSCompactAtFullCollection` 兜底）、并发阶段要占用 CPU（`-XX:ConcGCThreads` 可调）、`remark` 阶段依然 STW。
- **G1 的停顿为什么"可预测"**：它能估算每个 Region 的回收收益与耗时，按 `-XX:MaxGCPauseMillis` 优先回收收益最高的一批 Region，所以停顿相对可控——这也是它取代 CMS 的主要原因。
- **该怎么选收集器**：先看目标（吞吐优先还是延迟优先），再看数据（堆大小、对象存活率、Full GC 频率与单次停顿）。**没有最优收集器，只有最合适的**，而且必须用真实流量压测验证。

## CMS 和 G1 有什么区别？

结论：**CMS 只回收老年代、用标记-清除、不做整理**；**G1 把整个堆切成 Region，新生代与老年代都能管，整体以复制/整理为主**（Region 之间复制，Region 内部整理）。G1 还带来可预测停顿与全堆记忆集，因此在 JDK 9 取代了 CMS。

- **内存布局**：CMS 沿用经典分代——连续的新生代 + 连续的老年代；G1 把堆划成大小相等的 **Region**（1~32MB，2 的幂），每个 Region 逻辑上属于 Eden / Survivor / Old / Humongous，**物理上不再连续**。
- **收集范围**：CMS 是**老年代专用**收集器，必须与 ParNew 配合；G1 是**全堆收集器**，一次可以只回收一部分 Region（`Young GC` 与 `Mixed GC`）。
- **回收算法**：CMS 用标记-清除、会产生碎片；G1 在 Region 之间复制、Region 内部整理，**整体不产生碎片**。
- **停顿模型**：CMS 无法预测停顿；G1 通过 `-XX:MaxGCPauseMillis`（默认 200ms）做**收益优先**的 Region 选择，停顿相对可控。
- **并发标记的漏标处理**：两者都用**三色标记**，但补救手段不同——**CMS 用增量更新，G1 用 SATB（原始快照）**。

三色标记与漏标：标记过程中对象分三色——**黑**（自身与成员都扫完）、**灰**（自身扫完、成员未扫完）、**白**（未访问）。漏标需要**同时满足**两个条件：

1. 一个黑色对象**新增**了对白色对象的引用；
2. 该白色对象到灰色对象的所有引用路径**都断了**。

破坏其中任意一个就能避免漏标：

- **增量更新（CMS）**：记录"黑色对象新增的引用"，重新标记阶段以这些黑对象为根再扫一遍——破坏条件 1，靠**写后屏障**实现。
- **SATB（G1）**：在引用被删除时记录旧引用，按**原始快照**标记——破坏条件 2，靠**写前屏障**实现；还顺带让 G1 能在并发标记期间做 `Mixed GC`。

小结对比：停顿可控性 **G1 > CMS**；内存碎片 **G1 无、CMS 有**；全堆能力 **G1 有、CMS 无**；版本上 **CMS 于 JDK 9 废弃、JDK 14 移除，G1 于 JDK 7 引入、JDK 9 起默认**。

### 高频延伸
- **G1 的 Region 大小怎么定**：堆大小除以 2048，再向上取到最近的 2 的幂，范围 1~32MB；也可用 `-XX:G1HeapRegionSize` 显式指定，Region 总数目标约 2048 个。
- **Humongous 区是什么**：G1 把超过 Region 一半大小的对象视为大对象，存放在连续的 Humongous Region 中；分配不当会造成 Region 浪费并频繁触发 Full GC，是 G1 调优的重点之一。
- **记忆集（RSet）和卡表有什么用**：跨 Region（或跨代）引用会让"只扫一部分 Region"漏掉引用关系，因此用**卡表**记录哪些卡页含有跨区引用、用 **RSet** 汇总"谁指向我"，从而避免全堆扫描——这是 G1 能局部回收的前提。
- **SATB 相比增量更新有什么缺点**：SATB 以原始快照为准，会把**本可回收的浮动垃圾**判为存活、多占一些内存；好处是实现更简单，且更适合 G1 的局部回收。
- **G1 一定比 CMS 好吗**：不一定。小堆（如 4GB 以下）上 G1 未必更优，而且它的写屏障与 RSet 维护都有额外开销；G1 的优势集中在大堆且需要可控停顿时。**选型靠压测，不靠结论**。

## 类加载的过程是怎样的？

结论：类的生命周期是**加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载**，前五步合称**类加载**，其中验证、准备、解析三步合称**连接**。真正执行类中代码的只有**初始化**这一步。

- **加载**：按全限定名把 `.class` 字节流读入内存，生成方法区中的运行时数据结构，并在堆中创建对应的 `Class` 对象作为访问入口。
- **验证**：确保字节流安全合规，分四小步——文件格式验证、元数据验证、字节码验证、符号引用验证。
- **准备**：为**静态变量分配内存并赋零值**（`int` 赋 0、引用赋 `null`）。**常量是例外**：`static final` 的基本类型或 `String` 常量在准备阶段就赋真值。
- **解析**：把常量池中的**符号引用**替换为**直接引用**；解析可以推迟到初始化之后再执行（为了支持动态绑定）。
- **初始化**：执行类构造器 `<clinit>()`，即静态变量赋值语句与静态代码块按源码顺序合并执行——**这一步才真正开始执行类中代码**。

触发初始化的六种情形（主动引用）：

1. `new` 实例、读写静态字段（**被 `final` 修饰的编译期常量除外**）、调用静态方法；
2. 反射调用，如 `Class.forName`；
3. 初始化子类时，先初始化其父类；
4. 虚拟机启动时的主类；
5. `MethodHandle` / `invokedynamic` 解析结果对应的类；
6. 接口声明了 `default` 方法时，实现类初始化会先初始化该接口。

### 高频延伸
- **静态变量和静态代码块谁先执行**：按**源码书写顺序**。`<clinit>()` 是按出现顺序把两者合并的，写在前面就先执行——这就是"静态变量与静态块顺序"题的答案。
- **子类引用父类的静态字段会初始化子类吗**：不会，只会初始化**父类**。这类"被动引用"还有几种：通过数组定义引用类、引用编译期常量、用子类名引用父类的静态字段。
- **为什么准备阶段只赋零值**：因为赋值语句是 Java 代码，属于"初始化"的职责；准备阶段只管分配内存并给类型默认值（常量除外）。这也解释了为什么静态变量即使写在静态块之后，也能在方法里被访问而不报错。
- **`<clinit>()` 和 `<init>()` 有什么区别**：`<clinit>()` 是类初始化、由 JVM 调用、只执行一次、无需显式定义；`<init>()` 是实例构造器、每次 `new` 都执行，对应 `super()` 调用与实例变量赋值。
- **类加载的五步必须严格按序完成吗**：不必须。**解析**允许推迟到初始化之后（支持运行时才确定目标的动态绑定）；但**加载、验证、准备**必须在初始化之前完成。

## 双亲委派模型是什么？为什么要它、又怎么打破？

结论：双亲委派指类加载器收到加载请求时**先委派父加载器**，父加载器加载不了才自己加载。它保证了**同一个类在 JVM 中只被加载一次**，且核心类不会被自定义类顶替——是 Java 安全模型的基石。

- **层次结构（基线 JDK 8）**：`BootstrapClassLoader`（启动类加载器，C++ 实现，加载 `rt.jar` 等）→ `ExtensionClassLoader`（扩展类加载器，加载 `jre/lib/ext`）→ `ApplicationClassLoader`（应用类加载器，加载 classpath）。
- **委派过程**：`loadClass` 先看父加载器是否已加载 → 没有就向上委派，直到 Bootstrap → 都加载不了，才由自己 `findClass` 真正加载。所以是**"向上委派、向下加载"**。
- **为什么需要它**：
  1. **唯一性**——同一个类只会被加载一次，避免被不同加载器重复加载导致类型混乱（`instanceof` 失效）；
  2. **安全性**——`java.lang.String` 等核心类永远由 Bootstrap 加载，用户自己写一个同名类也无法被加载，不能植入恶意代码。

打破双亲委派的三种典型情形：

1. **重写 `loadClass`**：`loadClass` 是 `protected` 且非 `final`，子类可以改写委派逻辑。Tomcat 的 `WebAppClassLoader` 就是先尝试自己加载、再委派父加载器，用于应用隔离。
2. **线程上下文类加载器（SPI）**：JDBC、JNDI 这类"接口在上、实现在下"的场景里，接口由 Bootstrap 加载，实现类却在 classpath 上由应用类加载器加载。父加载器看不见子加载器的类，于是通过 `Thread.currentThread().getContextClassLoader()` 拿到应用类加载器去加载——这是**父加载器的反向委派**。
3. **OSGi / 热部署**：用自定义加载器构建网状委派关系，实现模块化与热替换。

### 高频延伸
- **两个类"相等"的判定条件是什么**：必须**类加载器相同**且**全限定名相同**。同一个 `.class` 被两个加载器加载会得到两个互不相同的 `Class` 对象，`instanceof` 与强转都会失败——这正是 Tomcat 隔离各 Web 应用的原理。
- **`Class.forName` 和 `ClassLoader.loadClass` 有什么区别**：前者默认会**初始化**类（会执行静态代码块），后者只加载不初始化。老代码里 `Class.forName("com.mysql.jdbc.Driver")` 就是借它触发静态块来注册驱动。
- **自己写一个 `java.lang.String` 能顶替核心类吗**：不能。请求会一路委派到 Bootstrap，而 Bootstrap 已经加载过 `java.lang.String`，于是直接返回原有的 `Class`；JVM 对 `java.` 开头的包名还另有保护。
- **JDK 9 之后委派模型变了吗**：总体思路没变，但模块化后 `ExtClassLoader` 被 `PlatformClassLoader` 取代、加载范围改为平台模块，同时新增了"按模块委派"的规则。
- **什么场景需要打破双亲委派**：需要**类隔离**（同名不同版本的类共存，如 Tomcat 多应用、中间件插件）、需要**热部署 / 热替换**、以及 SPI 这类"接口在上、实现在下"的场景。

## 强、软、弱、虚引用有什么区别？

结论：Java 提供四种引用，强度依次递减——**强 → 软 → 弱 → 虚**。差别在于**回收时机**与**能否拿到对象**：强引用日常在用；软引用适合做缓存；弱引用下次 GC 必被回收；虚引用只为收到回收通知，根本拿不到对象。

- **强引用（Strong）**：普通的 `A a = new A()`。只要强引用还在，对象**永远不会被回收**（哪怕即将 OOM），要断开只能显式置 `null`。
- **软引用（SoftReference）**：**内存不足时**才回收，适合做缓存——内存充裕时保留、紧张时自动释放。
- **弱引用（WeakReference）**：**下一次 GC 一定回收**，与内存是否充足无关。典型应用是 `ThreadLocalMap` 的 `Entry.key` 和 `WeakHashMap` 的键——它们期望"键没人用了就自动消失"。
- **虚引用（PhantomReference）**：**随时可能被回收**，而且**无法通过它获取对象**（`get()` 永远返回 `null`）。唯一用途是配合 `ReferenceQueue` 在对象被回收时收到通知，用来归还堆外内存等资源。
- **`ReferenceQueue` 的作用**：软、弱、虚引用都能关联一个引用队列；对象被回收后该 `Reference` 会**入队**，程序由此感知"对象已经没了"。

```java
// 弱引用：只要发生 GC，referent 就被回收、引用入队
ReferenceQueue<Object> queue = new ReferenceQueue<>();
Object obj = new Object();
WeakReference<Object> ref = new WeakReference<>(obj, queue);
obj = null;                        // 断开强引用
System.gc();
System.out.println(ref.get());     // 通常为 null
System.out.println(queue.poll());  // 已被回收并入队

// 软引用常用于缓存：内存紧张时才会被清理，取值必须判空
SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = cache.get();         // 可能已被回收
```

### 高频延伸
- **`ThreadLocal` 为什么用弱引用做 key**：若 key 是强引用，`ThreadLocal` 实例即便不再使用也会被 `ThreadLocalMap` 一直持有、无法回收，泄漏更严重；弱引用至少让 key 能在下次 GC 被清掉（详见并发模块的[『ThreadLocal 的原理是什么？为什么会导致内存泄漏？』](/java/concurrent/#threadlocal-的原理是什么-为什么会导致内存泄漏)）。
- **虚引用到底有什么用**：它是检测"对象被回收"的**唯一可靠手段**（`finalize` 并不可靠）。Netty 的 `DirectByteBuffer` 释放、JDK 的 `Cleaner` 机制都基于它归还**堆外内存**——这也解释了为什么直接内存的回收要依赖 GC。
- **`WeakHashMap` 和 `HashMap` 有什么区别**：`WeakHashMap` 的键是弱引用，键不再被外部强引用时，整个键值对会在下次 GC 后被移除。注意若值本身是强引用、且值又反向引用了键，会形成循环而回收不掉。
- **软引用什么时候被回收，能拿它做缓存吗**：JVM 会在**即将抛出 `OutOfMemoryError` 之前**清理软引用，因此 `get()` 不保证有值、必须判空，也就不能持有"必要数据"。作为缓存主力也不推荐——回收时机不可控，现代实践更常用 `Caffeine`、`Guava` 这类带容量与淘汰策略的缓存库。
- **四种引用分别在什么场景用**：强引用是默认；软引用做内存敏感的缓存；弱引用做"附属信息"（`WeakHashMap`、`ThreadLocal`）；虚引用做资源回收通知（`Cleaner`、堆外内存）。

## GC 日志怎么看？常用参数有哪些？

结论：GC 日志的**开启方式在 JDK 9 变了**——JDK 8 用 `-XX:+PrintGCDetails -Xloggc:<file>`，**JDK 9 起统一为 `-Xlog:gc*:<file>`**。读日志只需抓住三件事：**回收前后各区占用、单次耗时、以及老年代能否回落**。

开启与查看（注意版本差异）：

- **JDK 8**：`-XX:+PrintGCDetails`（打印详情）、`-XX:+PrintGCDateStamps`（带时间戳）、`-Xloggc:/path/gc.log`（输出到文件）。
- **JDK 9+**：统一日志框架，如 `-Xlog:gc*:file=/path/gc.log:time,uptime,level,tags`；旧的 `PrintGCDetails` 等参数已被取代（部分仍兼容但会打弃用告警）。
- **在线快速看**：`jstat -gcutil <pid> 1000` 每秒一行，给出各区占用百分比与 YGC/FGC 次数、总耗时——排查时通常**先用它定位，再去看详细日志**。

一条日志该看什么（以 JDK 8 的 `PSYoungGen` 为例）：

- **回收类型**：是 `GC`（Minor / Young）还是 `Full GC`。只有 `Full GC` 涉及老年代，也才是"停顿抖动"的常见来源。
- **回收前后占用**：`[PSYoungGen: 8192K->1024K(9216K)]` 表示新生代从 8192K 降到 1024K、总容量 9216K；后面的 `[ParOldGen: ...]` 与 `[Metaspace: ...]` 同理。
- **整体变化**：行末的 `10000K->2048K(19456K), 0.0123456 secs` 是全堆回收前后的占用与本次耗时。
- **判读口径**：**老年代回收后能否明显回落**是关键分水岭——回不去说明对象真被强引用牵着（怀疑泄漏）；能回落但很快又满，说明是**堆偏小或对象创建太快**（考虑调堆、优化对象占用）。

```bash
# JDK 8：输出 GC 详情到文件
java -XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/var/log/app/gc.log -jar app.jar

# JDK 9+：统一日志（注意接口与 JDK 8 完全不同）
java -Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags -jar app.jar

# 在线观察：每秒一行汇总，先靠它定位问题区间
jstat -gcutil <pid> 1000
```

常用参数（按用途分组）：

- **堆大小**：`-Xms`（初始）、`-Xmx`（上限）——**生产建议设成相等**。
- **新生代**：`-Xmn`，或 `-XX:NewRatio`、`-XX:SurvivorRatio`。
- **元空间**：`-XX:MetaspaceSize`（首次 Full GC 阈值）、`-XX:MaxMetaspaceSize`。
- **收集器**：`-XX:+UseG1GC`、`-XX:+UseParallelGC`、`-XX:MaxGCPauseMillis`（G1 的目标停顿）。
- **日志**：见上，按版本选择。
- **OOM 现场**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path`——**强烈建议所有生产服务都配上**，否则 OOM 之后没有现场。

### 高频延伸（面试官爱追问）
- **`-Xms` 和 `-Xmx` 为什么要设成一样**：核心是**行为可预测**。不固定时堆会**按需扩容**，运行中被迫扩堆会带来额外的内存申请与 GC 时机波动（默认堆的回缩并不积极，所以"伸缩"里真正要防的是**扩**）；固定下来既能避开这类抖动，也能更早暴露内存问题，例如"跑久了才 OOM"这类难查问题。
- **看到 Full GC 频繁，先调堆还是先查泄漏**：**先看老年代回收后能否回落**。能回落 → 大概率是堆或新生代偏小，可以调参数；回不去 → 基本是泄漏，调多大都没用，必须取堆快照排查（见[『线上 OOM 或 GC 频繁，你会怎么排查？』](#线上-oom-或-gc-频繁-你会怎么排查)）。
- **新生代是不是设大一点更好**：不一定。新生代大 → Minor GC 频率降低，但**单次 Minor GC 耗时变长**（要扫、要复制更多对象），且挤压老年代、可能更容易触发 Full GC。没有通解，只能压测。
- **JDK 9 之后旧参数还能用吗**：部分仍兼容但会打弃用告警（如 `PrintGCDetails`），**建议直接迁移到 `-Xlog`**。它的语法是 `-Xlog:<tag>=<level>:<output>:<decorators>`，可按标签与级别精细控制，比旧参数灵活得多。
- **GC 日志要不要长期保留**：要，而且建议**按大小滚动**——`-Xlog` 支持 `filecount` 与 `filesize`（如 `-Xlog:gc*:file=gc.log:time:filecount=5,filesize=10M`）。线上事故常常是"跑几小时后才开始抖"，没有历史日志就只能等复现。

## 线上 OOM 或 GC 频繁，你会怎么排查？

结论：先**明确现象与范围**（哪种 OOM、哪个实例、从何时开始），再**保留现场**（自动 dump + `jstat` 观察），最后**定位对象与代码**（MAT 看支配树、`jstack` 看线程栈）。切忌一上来就重启——现场没了，问题还会再来。

排查主线：

1. **确认是哪种 OOM**：光看异常信息就能区分——`Java heap space`（堆）、`Metaspace`（元空间）、`GC overhead limit exceeded`（GC 效率过低）、`unable to create new native thread`（线程数过多）、`Direct buffer memory`（直接内存）。
2. **看 GC 状况**：用 `jstat -gcutil <pid> 1000` 观察各区占用、YGC/FGC 频次与耗时。**老年代回收后能否回落**是关键分水岭。
3. **留证**：`jmap -dump` 导出堆快照（生产上更该预先配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`）；`jmap -histo:live` 可快速看对象直方图。
4. **定位对象**：用 MAT / JProfiler 打开快照，看**支配树（Dominator Tree）**与 Leak Suspects，找到占用最大的对象及其 **GC Roots 引用链**——引用链末端通常就是泄漏源。
5. **回到代码**：结合 `jstack` 看线程栈，确认是哪个业务入口在持续制造对象。

```bash
jps -l                                          # 先找到 Java 进程
jstat -gcutil <pid> 1000                        # 每秒看一次各区占用与 GC 次数
jmap -histo:live <pid> | head -20               # 对象直方图：谁在占内存
jmap -dump:live,format=b,file=heap.hprof <pid>  # 导出堆快照（会 STW，慎用）
jstack <pid> > stack.txt                        # 线程栈：谁在跑、谁在等锁
```

### 高频延伸
- **怎么区分内存泄漏和内存不足**：**内存不足**是对象确实太多、堆不够用，调大 `-Xmx` 或加机器能缓解；**内存泄漏**是对象本该回收却被强引用链牵着不放，调大堆只能推迟爆发。判据就是**老年代回收后能否回落**——回不去就是泄漏。
- **常见的泄漏源有哪些**：静态集合只增不删（自建缓存忘了清理）、`ThreadLocal` 用完不 `remove`（线程池场景）、监听器或回调注册后未注销、连接与流未关闭、内部类隐式持有外部类引用、堆外内存未释放。
- **`GC overhead limit exceeded` 是什么**：GC 花了超过 98% 的时间、却只回收了不到 2% 的堆空间，JVM 判定"再 GC 也没用"就直接抛错。它本质上是堆太小或对象存活率过高，不是独立的一类问题。
- **`unable to create new native thread` 怎么查**：这是**线程数**问题而非堆问题——查 `ulimit -u`、`/proc/sys/kernel/threads-max`，以及代码里有没有无限制创建线程的地方（如没设上限的线程池）。同理，"直接内存溢出"要查 `-XX:MaxDirectMemorySize` 与 `DirectByteBuffer` 的使用。
- **线上能直接 `jmap -dump` 吗**：要谨慎。`jmap -dump:live` 会触发一次 Full GC，大堆下可能造成秒级停顿甚至把服务拖挂。更稳的是**提前配好 OOM 自动 dump**，或用 `jcmd <pid> GC.heap_dump` 并挑低峰期执行；有 Arthas 时优先用 `heapdump` 与 `dashboard` 观察。

# 设计实战

## 如何设计一个短链（短网址）系统？

<Badge type="warning" text="难度：深入" />

### 一句话答案
核心链路：发号器生成全局唯一 ID → 用 62 进制压缩成短码 → 存储映射 → 访问短码时 302 重定向到原 URL。

### 详细解析
- **发号**：分布式自增 ID（雪花算法 / 号段模式 Leaf-segment）保证全局唯一且不连续。
- **压缩**：ID 转 62 进制（0-9a-zA-Z），如 10 亿级 ID 仅需约 6 位字符。
- **存储**：K/V 或关系表存 `shortCode → longUrl`，短码建唯一索引。
- **跳转**：访问 `/abc123` 查表后 **302** 重定向（便于统计点击可用 301 + 埋点）。
- **优化**：布隆过滤器防非法码、缓存热点映射、CDN/边缘节点直接重定向降低源站压力。

:::: tip 延伸
短码也可不依赖自增 ID，而用「原 URL 哈希 + 冲突重试 / 随机串」生成，优点是无须中心发号器。
::::

## 如何设计一个限流器（Rate Limiter）？

<Badge type="warning" text="难度：深入" />

### 一句话答案
常见算法：计数器、滑动窗口、漏桶（Leaky Bucket）、令牌桶（Token Bucket）；分布式下用 Redis 原子计数 + 过期实现。

### 详细解析
- **固定窗口计数器**：简单，但有窗口临界突变问题。
- **滑动窗口**：细分时间片，平滑且更精确。
- **漏桶**：以恒定速率流出，强行限制速率，突发会被排队/拒绝。
- **令牌桶**：按速率发令牌，桶可积攒，允许一定突发，最常用（如 Guava RateLimiter）。
- **分布式**：Redis `INCR + EXPIRE`（或 Lua 原子脚本）统计单位时间请求数，超过阈值拒绝。

:::: warning 注意
单机限流不足以保护集群，网关层（如 Nginx/Spring Cloud Gateway）常配合 Redis 做全局统一限流。
::::

## 如何设计一个秒杀/抢购系统？

<Badge type="warning" text="难度：深入" />

### 一句话答案
核心思路：静态资源/CDN 前置 → 网关限流削峰 → 秒杀 URL 随机化防刷 → Redis 预扣库存（原子减）→ 异步下单（MQ）→ 订单落库，库存用 Redis/Lua 保证原子，超卖靠预扣+回滚。

### 详细解析
- **流量削峰**：答题/验证码、排队、MQ 异步，把瞬时峰值拉平。
- **库存扣减**：`DECR` 原子操作判断是否 >0，避免超卖；售罄快速失败。
- **隔离**：秒杀业务独立部署、独立库表，不影响主站。
- **防超卖**：Redis 预扣 + 数据库乐观锁兜底；下单失败回补库存。

## 如何设计排行榜（热榜）？

<Badge type="warning" text="难度：深入" />

### 一句话答案
实时性要求高用 Redis 有序集合 ZSET（score 为热度/时间衰减），定期持久化；大规模可用分片 ZSET + 定时聚合，展示 TopN 直接 `ZREVRANGE`。

### 详细解析
- **ZSET**：`ZINCRBY` 加权重、`ZREVRANGE` 取 TopN，复杂度低。
- **时间衰减**：score 引入时间因子（如 `weight - 时间窗`），旧内容自然下沉。
- **持久化**：定时 `ZUNIONSTORE`/落库，防 Redis 丢数据。

## 如何设计一个发号器（分布式 ID 服务）？

<Badge type="warning" text="难度：深入" />

### 一句话答案
提供全局唯一、趋势递增、高可用的 ID：号段模式（Leaf-segment，DB 批量取号 + 双 buffer 预取）或 雪花算法（时间+机器+序列），并考虑时钟回拨与高并发。

### 详细解析
- **号段模式**：DB 存当前最大 id 和步长，每次取一段在内存分配，双 buffer 在用到一半时异步取下一号段，基本无 DB 抖动。
- **雪花**：64 位结构，高并发单机可达百万 QPS，但要处理时钟回拨（等待/报警/切换 workerId）。
- **趋势递增**利于数据库写入（减少页分裂）。

## 如何设计高性能缓存架构？

<Badge type="warning" text="难度：深入" />

### 一句话答案
缓存设计围绕「缓存三大问题 + 一致性 + 高可用」：更新用「先更新 DB 再删缓存（Cache-Aside）」、延迟双删兜底；多级缓存（本地+Redis）抗热点；高可用靠集群/哨兵。

### 详细解析
- **更新策略**：Cache-Aside（旁路），读 miss 回填，写时更新 DB 后删缓存；防不一致可延迟双删。
- **三大问题**：穿透（布隆/空值）、击穿（互斥锁/逻辑过期）、雪崩（随机过期/集群）。
- **多级**：本地缓存(Caffeine)挡热点 + Redis 挡全量，降低 Redis 压力。

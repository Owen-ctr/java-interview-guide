## 如何设计一个短链（短网址）系统？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：中 ｜ 标签：系统设计·短链

### 一句话答案
核心链路：发号器生成全局唯一 ID → 用 62 进制压缩成短码 → 存储映射 → 访问短码时 302 重定向到原 URL。

### 详细解析
- **发号**：分布式自增 ID（雪花算法 / 号段模式 Leaf-segment）保证全局唯一且不连续。
- **压缩**：ID 转 62 进制（0-9a-zA-Z），如 10 亿级 ID 仅需约 6 位字符。
- **存储**：K/V 或关系表存 `shortCode → longUrl`，短码建唯一索引。
- **跳转**：访问 `/abc123` 查表后 **302** 重定向（便于统计点击可用 301 + 埋点）。
- **优化**：布隆过滤器防非法码、缓存热点映射、CDN/边缘节点直接重定向降低源站压力。

::: tip 延伸
短码也可不依赖自增 ID，而用「原 URL 哈希 + 冲突重试 / 随机串」生成，优点是无须中心发号器。
:::

## 如何设计一个限流器（Rate Limiter）？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：中 ｜ 标签：系统设计·限流

### 一句话答案
常见算法：计数器、滑动窗口、漏桶（Leaky Bucket）、令牌桶（Token Bucket）；分布式下用 Redis 原子计数 + 过期实现。

### 详细解析
- **固定窗口计数器**：简单，但有窗口临界突变问题。
- **滑动窗口**：细分时间片，平滑且更精确。
- **漏桶**：以恒定速率流出，强行限制速率，突发会被排队/拒绝。
- **令牌桶**：按速率发令牌，桶可积攒，允许一定突发，最常用（如 Guava RateLimiter）。
- **分布式**：Redis `INCR + EXPIRE`（或 Lua 原子脚本）统计单位时间请求数，超过阈值拒绝。

::: warning 注意
单机限流不足以保护集群，网关层（如 Nginx/Spring Cloud Gateway）常配合 Redis 做全局统一限流。
:::

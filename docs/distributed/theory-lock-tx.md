# 理论与锁事务

## 分布式系统中 CAP 理论是什么？

<Badge type="tip" text="难度：进阶" />

### 一句话答案
CAP 指一致性(C)、可用性(A)、分区容错性(P)，三者不可兼得；分布式系统通常优先保证 P，在 C 与 A 之间权衡。

### 详细解析
- **C 一致性**：所有节点同一时刻数据相同。
- **A 可用性**：每个请求都能得到（非异常的）响应，不保证是最新数据。
- **P 分区容错**：网络分区（节点间失联）时系统仍能对外服务——网络不可靠，所以 P 必选。
- **取舍**：CP 系统（如 ZooKeeper、etcd）牺牲可用性保强一致；AP 系统（如 Eureka、Cassandra）牺牲强一致保可用。

:::: tip 延伸
BASE 理论是对 AP 系统的补充：基本可用(BA)、软状态(S)、最终一致(E)，常见于高可用互联网架构。
::::

## 分布式锁有哪些实现方式？

<Badge type="warning" text="难度：深入" />

### 一句话答案
常见：基于 Redis（SET NX + 过期）、基于 ZooKeeper（临时有序节点）、基于 etcd；核心要保证互斥、防死锁、可重入。

### 详细解析
- **Redis**：`SET key value NX EX` 原子加锁，用 Lua 脚本保证「校验+删除」原子性；需解决锁误删（value 用唯一标识）和锁过期业务未执行完（看门狗续期）。
- **ZooKeeper**：创建临时有序节点，最小序号获锁，释放（会话断开）自动删节点；天然防死锁、可监听唤醒。
- **etcd**：基于租约(lease) + 事务 CAS 实现，类似 Redis 思路。

:::: warning 注意
Redis 主从切换瞬间可能脑裂导致锁失效，对正确性要求极高的场景可用 Redlock 或 ZK/etcd。
::::

## 分布式事务有哪些解决方案？

<Badge type="warning" text="难度：深入" />

### 一句话答案
主流：2PC/3PC（强一致但阻塞）、TCC（业务补偿，性能好）、本地消息表/事务消息（最终一致）、Saga（长事务编排）、Seata 等框架封装。

### 详细解析
- **2PC**：准备 + 提交两阶段，协调者单点、同步阻塞、数据锁定久。
- **TCC**：Try（预留资源）→ Confirm（确认）/ Cancel（补偿），侵入业务但无长锁。
- **本地消息表**：本地事务写业务+消息，异步投递，保证最终一致，简单实用。
- **选型**：强一致用 TCC/Seata AT；可接受最终一致用消息表/事务消息。

## 如何保证接口的幂等性？

<Badge type="warning" text="难度：深入" />

### 一句话答案
幂等指同一请求多次执行结果一致；常用：唯一索引/唯一业务单号 + 去重表、token 机制、乐观锁版本号、状态机校验、分布式锁。

### 详细解析
- **去重表**：以业务唯一键建唯一索引，插入失败即重复。
- **token**：下单前先取 token，提交时校验并删除，防重复提交。
- **乐观锁**：`UPDATE ... SET ver=ver+1 WHERE ver=?`，版本不符则失败。
- **状态机**：只允许合法状态流转，重复操作命中终态直接返回。

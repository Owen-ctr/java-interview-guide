## 为什么 MySQL 索引默认用 B+ 树而不是 B 树或哈希？

<Badge type="warning" text="难度 ⭐⭐⭐" /> 出现频率：高 ｜ 标签：MySQL·索引

### 一句话答案
B+ 树非叶子节点不存数据、扇出大、树矮，且叶子成有序链表，极适合范围查询和磁盘 IO；哈希不支持范围，B 树节点存数据导致扇出小。

### 详细解析
- **B+ 树**：非叶节点只存 key 和指针，单页能放更多 key → 层高更低（通常 3~4 层），减少磁盘 IO。
- **叶子链表**：天然有序，范围查询（`BETWEEN`、排序）只需顺序遍历。
- **哈希索引**：等值快但不支持范围、无法排序、有哈希冲突。
- **为什么不用二叉树**：树高太大，磁盘 IO 次数多。

## 事务的 ACID 和隔离级别？

<Badge type="warning" text="难度 ⭐⭐⭐" /> 出现频率：高 ｜ 标签：MySQL·事务

### 一句话答案
ACID = 原子性/一致性/隔离性/持久性；隔离级别由低到高：读未提交 < 读已提交 < 可重复读(MySQL 默认) < 串行化。

### 详细解析
- **A 原子性**：事务要么全做要么全不做（undo log 保证）。
- **C 一致性**：事务前后数据满足约束。
- **I 隔离性**：并发事务相互隔离（锁 + MVCC）。
- **D 持久性**：提交后落盘不丢（redo log 保证）。
- **隔离级别**：MySQL InnoDB 默认「可重复读」，通过 MVCC + 间隙锁解决大部分幻读。

## 脏读、不可重复读、幻读分别是什么？

<Badge type="warning" text="难度 ⭐⭐⭐" /> 出现频率：中 ｜ 标签：MySQL·事务

### 一句话答案
脏读=读到未提交数据；不可重复读=同事务内同条记录两次读结果不同（侧重修改）；幻读=同查询条件两次结果集行数不同（侧重新增/删除）。

### 详细解析
- **脏读**：事务 A 读到事务 B 未提交的修改，B 回滚后 A 拿到脏数据。
- **不可重复读**：A 两次读同一行，期间 B 提交了对该行的修改。
- **幻读**：A 按条件查到 N 行，期间 B 插入/删除符合条件的行，A 再查变成 M 行。
- **解决**：提升隔离级别；InnoDB 在可重复读下用 MVCC + 间隙锁（Next-Key Lock）防幻读。

## 缓存穿透、击穿、雪崩是什么？怎么应对？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：高 ｜ 标签：Redis·缓存

### 一句话答案
穿透=查不存在的数据绕缓存打 DB；击穿=热点 key 失效瞬间大量请求打 DB；雪崩=大量 key 同时失效/Redis 宕机导致 DB 被冲垮。

### 详细解析
- **穿透**：非法/不存在 key。应对：缓存空值、布隆过滤器拦截。
- **击穿**：单个热点 key 过期。应对：互斥锁重建、逻辑过期（不真删）、热点不过期。
- **雪崩**：批量 key 同时失效或 Redis 挂。应对：过期时间加随机抖动、多级缓存、Redis 高可用（哨兵/集群）。

::: tip 延伸
布隆过滤器有误判率（存在可能误判为存在，不存在一定准确），适合做第一道拦截。
:::

## 聚簇索引、覆盖索引、回表、最左前缀原则？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：高 ｜ 标签：MySQL·索引

### 一句话答案
聚簇索引叶子存整行数据（InnoDB 主键即聚簇）；覆盖索引指查询字段都在索引中、无需回表；回表是二级索引查完需拿主键再去聚簇索引取数据；最左前缀指联合索引须从最左列开始匹配。

### 详细解析
- **聚簇 vs 非聚簇**：InnoDB 聚簇索引即主键（无主键用隐藏 row_id）；MyISAM 索引与数据分离。
- **覆盖索引**：`SELECT id,name FROM t WHERE name=?` 若 (name,id) 联合索引，直接命中无需回表，性能更好。
- **最左前缀**：联合索引 (a,b,c) 可命中 a、a,b、a,b,c，但跳 a 查 b 不命中；范围查询（>、<）后字段失效。

## MVCC 多版本并发控制原理？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：高 ｜ 标签：MySQL·事务

### 一句话答案
InnoDB 通过隐藏事务 id、回滚指针 + undo log 构建数据多版本，配合 ReadView 实现「快照读」，让读不加锁、读写不阻塞。

### 详细解析
- **隐藏列**：每行有 `trx_id`（最后修改事务）和 `roll_pointer`（指向 undo 旧版本）。
- **ReadView**：记录当前活跃事务集合，判断某版本对当前事务是否可见（已提交才可见）。
- **快照读**：普通 `SELECT` 读快照，不加锁；`SELECT ... FOR UPDATE` 是当前读，读最新并加锁。

## redo log、undo log、binlog 各自作用？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：高 ｜ 标签：MySQL·日志

### 一句话答案
redo log 保证持久性（崩溃恢复已提交数据）、undo log 保证原子性（回滚/实现 MVCC）、binlog 是 Server 层归档日志（主从复制、时间点恢复）。

### 详细解析
- **redo log**：物理日志、循环写、WAL（先写日志再落盘），InnoDB 特有。
- **undo log**：逻辑日志，记录反向操作，用于回滚和 MVCC 旧版本。
- **binlog**：逻辑日志、追加写，主从同步依赖它；两阶段提交保证 redo 与 binlog 一致。

## 什么是分库分表？有哪些方式？

<Badge type="warning" text="难度 ⭐⭐⭐⭐" /> 出现频率：中 ｜ 标签：MySQL·架构

### 一句话答案
当单库/单表数据量过大导致性能瓶颈时，按业务（垂直拆分）或按数据（水平拆分，如按 user_id 取模/按时间）拆分到多个库表，降低单点压力。

### 详细解析
- **垂直分库/分表**：按业务模块/字段冷热拆分，减小单表宽度。
- **水平分表**：数据行分散到多张结构相同的表，路由 key 需稳定（避免跨片查询）。
- **代价**：分布式事务、跨片 join、分页/排序、全局唯一 ID 都变复杂，常引入 ShardingSphere 等中间件。
